Recommended development sequence

I would not give a coding agent a single prompt saying "Build DocuVerse." The incremental sequence above is much safer:

Foundation → S3 → Loading → Chunking → Embeddings → Pinecone → Retrieval Test → RAG → Chat UI → Citations → S3 Sync → Conversational RAG → Guardrails → Productionization

The most important checkpoints are Prompt 4, Prompt 7, and Prompt 8. In particular, validate retrieval in Prompt 7 before connecting the LLM. If DocuVerse retrieves the wrong chunks, changing the LLM usually won't fix the underlying RAG problem.

For a first usable MVP, you only need to complete Prompts 1–10. Prompts 11–18 move DocuVerse toward a much more production-ready internal document-search platform.

Enhance the **DocuVerse** application so that simple greetings and conversational messages are handled appropriately instead of being sent directly to the RAG document-search pipeline.

## Current Behavior

Currently, when the user enters:

`Hi`

DocuVerse searches the document repository and responds:

> I could not find enough information in the available documents to answer this question.

This is not a good user experience because greetings do not require document retrieval.

## Required Enhancement

Before sending the user's query to the LangChain RAG pipeline, classify whether the input is:

1. **Greeting / Welcome Message**
2. **Conversational Message**
3. **Document Question**

### 1. Greeting Messages

Recognize common greetings such as:

* Hi
* Hello
* Hey
* Good morning
* Good afternoon
* Good evening
* Hi DocuVerse
* Hello DocuVerse

For these messages, DO NOT call Pinecone, the retriever, embeddings, or the LLM RAG chain.

Return a friendly response such as:

> Hello! 👋 Welcome to DocuVerse. I can help you find information from your organization's documents. What would you like to know?

### 2. Conversational Messages

Handle simple conversational inputs such as:

* Thanks
* Thank you
* Okay
* Got it
* Bye
* Goodbye
* What can you do?
* Help

Examples:

**User:** Thanks
**DocuVerse:** You're welcome! Let me know if you'd like to search for anything else in your documents.

**User:** What can you do?
**DocuVerse:** I can search your organization's documents and answer questions based on the information available in them. Ask me a question about the documents to get started.

**User:** Help
**DocuVerse:** Ask me a question about the information stored in your organization's documents. I'll search the relevant content and provide a grounded answer.

**User:** Bye
**DocuVerse:** Goodbye! 👋 Come back anytime you need help searching your documents.

### 3. Document Questions

Questions such as:

* What is the vacation policy?
* How many sick days are available?
* Explain the company's training reimbursement policy.
* What does the employee handbook say about remote work?

should continue through the existing RAG workflow:

`User Question`
→ `FastAPI`
→ `LangChain`
→ `Embedding`
→ `Pinecone Retriever`
→ `Relevant Chunks`
→ `LLM`
→ `Grounded Answer`

Do not change the existing RAG implementation.

## Implementation

Create a lightweight intent-handling layer before the RAG pipeline.

Suggested flow:

```text
User Message
     ↓
Message / Intent Handler
     ↓
 ┌───────────────┬────────────────────┐
 ↓               ↓                    ↓
Greeting     Conversation       Document Question
 ↓               ↓                    ↓
Static       Static/Template       RAG Pipeline
Response       Response                ↓
                                  Pinecone + LLM
```

Create a function similar to:

```python
def get_conversational_response(message: str) -> str | None:
    """
    Detect simple greetings and conversational messages.

    Returns:
        str  -> if the message can be handled without RAG
        None -> if the message should continue to the RAG pipeline
    """
```

Then integrate it before document retrieval:

```python
response = get_conversational_response(user_message)

if response:
    return response

return rag_service.answer_question(user_message)
```

Keep this logic separate from the RAG service so that the architecture remains modular.

Suggested structure:

```text
app/
├── api/
├── services/
│   ├── conversation_service.py
│   ├── rag_service.py
│   ├── retrieval_service.py
│   └── embedding_service.py
```

Put greeting/conversation detection inside `conversation_service.py`.

## Important Requirements

* Do not perform vector search for greetings.
* Do not create embeddings for greetings.
* Do not call Pinecone for greetings.
* Do not call the LLM unnecessarily for basic conversational messages.
* Keep the solution lightweight; simple normalized string/regex matching is sufficient for this stage.
* Matching should be case-insensitive.
* Trim whitespace and punctuation before matching.
* Do not accidentally classify document questions containing greeting words as greetings.

For example:

`Hi, what is our vacation policy?`

must be treated as a **document question**, not just a greeting.

It should therefore go through the RAG pipeline.

Keep the existing Streamlit chat interface.

**User:** What is the vacation policy?

```python

st.session_state.username = "admin"
st.session_state.role = "admin"
```

Authentication should persist while the user navigates through the application during the same session.

If the application contains a **FastAPI layer**, keep the architecture compatible with eventually moving authentication and authorization into FastAPI. However, do not redesign the existing architecture solely for this enhancement.

### 5. Authorization

Create reusable role-checking logic instead of placing username comparisons throughout the application.

For example:

```python
def is_admin():
    return (
        st.session_state.get("authenticated", False)
        and st.session_state.get("role") == "admin"
    )
```

or:

```python
def has_role(required_role):
    return (
        st.session_state.get("authenticated", False)
        and st.session_state.get("role") == required_role
    )
```

Use **roles**, not usernames, when deciding whether a feature can be accessed.

Do not implement logic such as:

```python
if username == "admin":
```

throughout the application.

### 6. Logout

Add a **Logout** option after successful login.

Preferably display something similar in the Streamlit sidebar:

```text
Logged in as: admin
Role: Admin

[Logout]
```

When Logout is clicked:

* Clear authentication-related session state
* Return the user to the login page
* Do not retain the previous user's role

### 7. Security

Do not scatter usernames and passwords throughout the source code.

For this prototype, keep authentication configuration centralized in one module, for example:

```text
auth.py
```

Structure it so that later the application can easily migrate to:

* Environment variables
* `.env`
* AWS Secrets Manager
* Amazon Cognito
* Database-based users
* OAuth / SSO

If possible, hash passwords instead of comparing plain-text passwords directly.

**Never log passwords.**

Do not expose credentials through error messages, logs, UI messages, API responses, or debugging output.
